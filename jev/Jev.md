# Jev 模型学习笔记

> **素材来源**：B 站「程序员鱼皮」｜《全网刷屏的 Jev 模型正式开放！保姆级教程 + 实战测评》BV1wDhj6wEa8（12:24）
> **已核实**：本篇的原语名称、参数写法、返回字段均按 **TypeSafe 官方文档**（docs.typesafe.ai）核对；性能与定价数字来自 **TypeSafe 官网**；第三方来源与厂商声明已单独标注
> **一句话定位**：Jev 不是"更好的聊天模型"，而是一个**不生成文字、只做判断**的决策模型——你可以把它当成**一个智能的 if 语句**。

---

## 一、它到底是什么

| 问题 | 结论 |
|---|---|
| 能聊天吗 | **不能**。Jev 未接受生成开放式文本的训练，不是聊天模型 |
| 那它干什么 | 接收**文本状态（state）** + **类型化问题（questions）**，返回**有界决策** |
| 返回什么 | 强类型 + 带概率的结果，程序可直接消费，无需解析文本 |
| 官方怎么定义 | **System One Model（系统一模型）** |
| 谁做的 | **TypeSafe AI**（CEO Diogo Almeida，前 OpenAI 研究员、RLHF / InstructGPT 核心作者之一） |
| 当前版本 | **jev-1.13.0**；别名 `jev-latest`、`jev-preview` 指向同一版本 |

**两个名字的由来**（视频没展开，很能说明产品意图）：

- **System One** ← 卡尼曼《思考，快与慢》的"系统 1 / 系统 2"框架：系统 1 是快速直觉判断（一眼看出对方在生气），系统 2 是深度推理（算一道数学题）。**传统 LLM 像系统 2，Jev 是系统 1**。
- **Jev** ← 经济学家**杰文斯（Jevons）**及**杰文斯悖论**——官方借它表达：智能成本每下降一个数量级，会解锁更多数量级的新用途。这也解释了它为什么要把价格压到这么低。

## 二、原理解析：为什么它这么快、这么便宜

这一节是理解 Jev 的关键，也是"它为什么不是一个小 LLM"的答案。

### 1. 并行采样：一次往返，同时回答所有问题

传统 LLM 是**逐字生成**——一个 token 一个 token 地"写"，写完再校验格式，多问一个问题就要多一轮往返。

Jev 用的是**并行采样器**：同一个请求里的**所有问题，在一次硬件感知的查询中并行求值**，一次往返返回全部答案。而且要按**相互隔离**的方式评估——一个问题不会污染另一个问题的判断（没有"上下文腐烂"）。

**由此推出的三个实用结论**：
- 一次请求里问 1 个问题和问 10 个问题，**延迟几乎没差别**（只多花一点 token 钱，不多花时间）
- 官方把这个用法叫 **speculative fan-out（投机扇出）**：把你代码里**可能**需要的问题一次性全问了，哪怕其中一些对当前 state 并不适用，最后让代码决定听哪几个——**不要因为"第二个问题的答案可能让第一个问题失去意义"而分成两次调用**
- 同一份 `state` 在一次请求内**只计一次费**——这是批量调用成本优势的直接来源

### 2. RLCD：训练目标不是"讨人喜欢"，而是"说到做到"

TypeSafe 把它的训练方法叫 **RLCD（Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习）**，而不是 RLHF。

- **RLHF** 优化的是"人类更喜欢哪个回答"——适合聊天。
- **RLCD** 优化的是**决策正确性 + 概率标定**：如果模型说 90%，那么在大量同类预测里就**应该真有约 90% 是对的**。

这带来一个传统 LLM 很缺的能力：**它的置信度是可以被程序采信的**。普通大模型的"自信"经常不可靠，Jev 的概率是校准过的——所以代码可以写"置信度不够就转人工"。

⚠️ 注意**校准是群体属性**：它保证"一类预测里 90% 的准确率"，**不保证某一个具体答案是对的**。

### 3. 类型安全 ≠ 语义正确（最容易误解的一点）

官网打出的 **"Zero Hallucinations / 0% 结构化错误率"**，官方自己做了限定说明：

> 这个 0% 指的是**输出不会跑出你声明的 schema**（不会凭空编出一个不存在的选项、不会返回坏的 JSON），**它不是实测的错误率**。

也就是说 Jev **保证形状，不保证决策**：
- 它不会选出你没定义过的部门（**类型错误在结构上不可能**）
- 但它**仍然可能**把该给技术部的工单判成财务部，也可能给一个紧急事件打出很低的概率

这是使用 Jev 时最需要建立的预期。

### 4. 官方性能数字

官网首页标题直接写着 **"193.6x Faster, 444.6x Cheaper"**，同任务对比：

| 指标 | Jev | LLM（对比基准） |
|---|---|---|
| 单次耗时 | **0.114 s** | 8.566 s |
| 单次成本 | **$0.000081** | $0.013880 |
| 结构化输出错误率 | **0.00%** | 0.5% ~ 12.6%（各模型不同） |
| 工具调用错误率 | **0.00%** | 0.34% ~ 22.1% |
| 输入价格 | **$0.042 / 百万 token** | $0.20 ~ $10 / 百万 token |
| 输出价格 | **免费** | $1.20 ~ $50 / 百万 token |

其他工程参数：端到端延迟 **70–500 ms**（厂商标称）；state + 最长问题约 **32K token**，总计约 **64K token**；限流约 **250,000 token/s、1,200 请求/分钟**。

## 三、怎么调用：state + 类型化问题

### 接口

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <API_KEY>
Content-Type: application/json
```

**请求体三个字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `state` | string \| object \| array | **要评估的内容**。纯文本用字符串；聊天记录、工单、应用状态等用对象/数组 |
| `model` | string | 模型名，用 `"jev-latest"` |
| `questions` | map | **你自定义键名**的类型化问题集合，答案会以**同一个键名**返回 |

### 官方请求示例

```json
{
  "state": "Help! My payouts have been failing for 3 days.",
  "model": "jev-latest",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "Does this convey urgency?",
      "criteria": {
        "true": "Explicitly time-sensitive",
        "false": "No urgency expressed"
      }
    },
    "department": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "billing": "Payments, invoicing, refunds",
        "technical": "Bugs, outages, integrations",
        "sales": "Pricing, upgrades, new accounts"
      }
    },
    "frustration": {
      "type": "score",
      "instructions": "How frustrated is the customer?",
      "criteria": ["Calm", "Frustrated", "Very angry"]
    }
  }
}
```

### 两个重要技巧

1. **state 用"带字段名的对象"，不要用一坨纯文本**。这样问题里可以用**反引号点号语法**引用具体字段，例如 `` `ticket.messages[0].text` ``。
2. **只放相关内容**。无关上下文对 Jev 来说是干扰项，它**不会自动打折**——官方明确要求"先检索和过滤，只发每个问题真正需要的内容"。

`instructions` 也不只是字符串，可以是**对象**：把问题和它需要引用的数据分字段放，再用反引号互相引用。

## 四、三种原语：`noul` / `choice` / `score`

### ⚠️ 先纠正一个命名

**官方（TypeSafe Direct）把是/否原语叫 `noul`**，**不是 Bool**。

之所以满屏都在说 "Boolean"：**Vercel AI SDK / AI Gateway 把等价的是/否评估面暴露成了 `Boolean`**。所以：
- 看 **TypeSafe 官方文档 / 官方 SDK** → 用 **`noul`**
- 走 **Vercel 网关** → 那一侧叫 **`Boolean`**
- **按你实际调用的提供方契约来写**，别混用

> 第 1 节视频里说的"第一种是是非题"，对应就是 `noul`。

### 三种原语的官方参数与返回

| 原语 | 回答什么 | `criteria` 写法 | 上限 | 返回字段 |
|---|---|---|---|---|
| **`noul`** | 是/否判断 | `{"true": "...", "false": "..."}`（可选） | — | `noul`（0~1 的是的概率）**无独立 confidence 字段** |
| **`choice`** | 从选项里选一个 | `map<选项, 描述>`，描述可为 `null` | **255 个选项** | `choice`、`probabilities`（各选项概率，和为 1）、`confidence` |
| **`score`** | 在有序量表上打分 | **有序数组**，至少 2 级 | **10 个等级** | `score`（概率加权，可落在两档之间）、`legend`、`probabilities`、`confidence` |

三者**共用** `type` 和 `instructions`（`instructions` 可以是 string / object / array），区别在 `criteria` 的形状。

### 官方返回示例

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "is_urgent": {
      "type": "noul",
      "noul": 0.95
    },
    "department": {
      "type": "choice",
      "choice": "billing",
      "probabilities": { "billing": 0.88, "technical": 0.12, "sales": 0.0 },
      "confidence": 0.81
    },
    "frustration": {
      "type": "score",
      "score": 1.05,
      "legend": { "0": "Calm", "1": "Frustrated", "2": "Very angry" },
      "probabilities": { "0": 0.0, "1": 0.95, "2": 0.05 },
      "confidence": 0.92
    }
  },
  "usage": { "input_tokens": 304, "output_tokens": 18 }
}
```

### 选哪个原语的判断法（按形状选，别凭感觉）

- 答案在**无序类别**之间 → **`choice`**（路由、分类、打标签）
- 答案是**一条频谱上的位置**，且你能用 2~10 个具体档位描述 → **`score`**（严重度、沮丧度、优先级）
- 答案是**干净的 是/否** → **`noul`**（是不是 bug 报告、有没有要退款、含不含个人信息）

两条硬规则：
- **有中间态就别用 `noul`**——那是 `score` 的活
- **无序类别别用 `score`**——那是 `choice` 的活

### 关于 `confidence` 和概率的读法

`noul` **没有**独立置信度字段——它的概率值**本身就是确定性信号**，而且 **0.5 不是"中等"，是"模棱两可"**。

`choice` / `score` 的 `confidence` 是**从概率分布推导出来的**，和"选中项的概率"**不是同一个字段**。判断时两个都要看：

| 场景 | 分布 | 建议策略 |
|---|---|---|
| 明显领先 | billing 98% / technical 1% | 可直接路由 |
| 几乎打平 | billing 43% / technical 39% | 追问澄清或转人工，比直接动手更划算 |

**阈值要用你自己的代表性数据来定**，并考虑判错的代价。

### 官方错误码

`401` 密钥缺失/无效 ｜ `422` 请求体校验失败 ｜ `429` 触发限流（需退避重试）｜ `529` 服务过载（稍后重试）。官方 SDK 默认带重试策略。

## 五、和生成式模型的区别

| 维度 | 生成式 LLM | Jev |
|---|---|---|
| 产出 | 文本、代码、解释等内容 | **有界类型化决策 + 概率** |
| 典型任务 | 起草回复、解释概念、写代码、总结文档 | 选路由、评估命题、按量表打分 |
| 谁消费 | 人或需要解析/校验结果的程序 | **直接分支、套策略、触发复核的应用代码** |
| 生成方式 | 逐字生成 token | 并行采样，在选项上出概率 |
| 多问题 | 逐个问，耗时累加 | 一次请求并行，延迟几乎不增 |
| 优化目标 | 通顺、人类满意（RLHF） | 判断准确、概率校准（RLCD） |
| 输出结构 | 需校验，可能出错 | 受 schema 约束，结构化错误率 0% |

**官方定位**：LLM 产出"给人看的词"，Jev 产出"给代码用的决策"，更像代码——可靠、快速、自洽、类型安全。

**两者是分工，不是替代**：LLM 负责**规划与撰写**，Jev 负责**路由、门控、检查、升级**。核心论断是——**软件里大多数 LLM 调用其实都是小型判断**，它们本该是带显式不确定性的有界决策，而不是一段等待被解析的散文。

## 六、什么场景该用它

### ✅ 适合

| 模式 | 说明 |
|---|---|
| 路由 | 决定该进哪个已知队列、团队或流程 |
| 分类 | 在**有业务含义区别**的命名类别里选 |
| 相关性与过滤 | 判断文本是否相关，再决定要不要下游处理 |
| 流程门控 | 判断证据是否满足某个条件，才让代码继续 |
| 语义校验 | 判断某个说法是否被提供的证据/规则支持 |
| 紧急度与定性打分 | 把事件或消息放到有序的、有描述的量表上 |
| Agent 下一步动作选择 | 在**应用已经授权**的动作里选一个 |

其他高价值场景：LLM 护栏（提示注入筛查、工具调用前风险分类）、检索重排（RAG 段落过滤）、语料级批量标注、简历与线索评分、Agent 的模型路由（该用快模型还是前沿模型）。

**甜点区**：高频、单次后果轻、语义模糊到手写 if 表达不出来。

### ❌ 不适合（官方为 Jev 1.13 记录的"锯齿"）

| 不要用它做 | 该用什么 |
|---|---|
| 开放式文本生成 | 生成式模型（回复、文章、代码） |
| 算术与精确计数 | 代码 |
| 日期时间比较 | 代码（先抽取有界成分，再在代码里解析比较） |
| 多层间接推理 | 拆成原子问题，或改用推理模型 |
| 从零抽取未知值 | Jev **只能在给定候选里选**，造不出新值 |
| 对抗性输入 | 写精确的 criteria + 测试边界 + 在动作外套应用层防护 |
| 又大又杂的 state | 先检索过滤，只发需要的 |

另外官方提醒：**Jev 会"字面地"读你的 criteria**——`instructions` 和 `criteria` 必须对齐，边界情况要写明确，上线前用代表性输入实测。

**能力边界速记**：不能生成文字、不能算术、不能做日期比较、不能替代传统 LLM；输入数据不准确会导致判断不准。

## 七、上手路径

两条线：**直连 API**（开发者）和**通过网关/AI 工具**（不想注册或要接进现有工具）。

### 路径 A：直连 TypeSafe

1. 注册 TypeSafe 账号（官网；官方站未标注注册状态，第三方知识库记录称 2026-09-22 起直接注册曾暂停，**当前状态请以官网为准**）
2. **Playground** 在线试：填 state + 问题，直接看返回
3. 控制台创建 **API Key**
4. 用官方 SDK 或裸 HTTP 调用 `POST /v1/systemone`

> 视频作者在 Jev 未正式开放时，就是用 **Vercel AI Gateway** 做了个**中文版 Jev 调试广场**，可在网页体验三种回复方式。

### 路径 B：通过网关 / AI 工具

| 类型 | 选项 |
|---|---|
| 网关 | **Vercel AI Gateway**（`typesafe-ai/jev`）、**OpenRouter**（`typesafe/jev-1.13`，Decisions API，alpha）、**Cloudflare Workers AI**（`typesafe/jev`） |
| 官方 SDK | `typesafe-sdk`（Python，需 3.10+）、`@typesafe-ai/sdk`（TS，需 Node 20+），均 MIT |
| 框架集成 | Pydantic AI `TypeSafeModel`、LangChain `langchain-typesafe`、AI SDK 7 `experimental_evaluate`、MCP（`@jkudish/jev-mcp`） |
| 自托管类比 | **AnyJev**（Nokia Applied Research，Apache-2.0），在开源 LLM 上实现 Jev 风格决策 |

**接入 AI 工具（视频里的做法）**：官方提供**通用 skills 技能包**，作用是把"Jev 是什么、怎么调用"告诉 AI 工具。官方给一段现成提示词（视频作者改成了中文全局安装版），**直接发给任意 AI 工具**，它会自动从 GitHub 仓库拉取技能文件；之后还需让 AI 帮忙在**环境变量里配置 API Key**。触发方式：斜杠命令，或直接在提示词里让 AI 用 Jev 判断。

### 生态注意点

- **只有托管 API，权重闭源**
- **提示注入风险**：对抗性输入可以偏移它的概率（官方 limitations 页亦有记录）
- **命名陷阱**：存在第三方转售站与同名 npm / PyPI 包，认准官方域名
- **锁定风险**：问题和 criteria 本质上是**程序逻辑**，要和代码一样**版本化**，才能重放历史决策
- **固定版本**：响应里会带带版本的模型 ID，建议记录并 pin 住版本

## 八、视频实测数据

UP 主自己搭了个测试网站，用 API 同时接入 Jev 和 DeepSeek，跑同一任务对比：

| # | 测试项 | 测什么 | 结果 |
|---|---|---|---|
| 1 | 数字华容道（API 直连对比 DeepSeek） | 决策能力 | Jev 操作速度明显更快，**完成速度遥遥领先**，输入 token 与累计价格也更低 |
| 2 | 批量分类 1000 封邮件 | 批量处理 | Jev **15.6 秒**完成，约 **64 封/秒**，比 DeepSeek **快接近 2 倍**，花费约 **1 毛** |
| 3 | 连连看（接入 Codex） | 实时决策 | **未达预期**，整局约 **5 分钟**，快时一秒消一个、但常卡顿 |
| 4 | 697 篇长文打标签（300 多万 tokens） | 批量分类 | **几分钟**完成 |

**总花费**：作者测了很多任务，总共花了**不到 2 元**。

**测试 3 为什么慢**（很有价值的一条经验）：
Jev **只能处理文本和 JSON，看不到画面**。连连看只能靠解析网页文件和 DOM 结构来定位方块，因此变慢。
那些用 Jev 玩游戏的博主，都是**先用代码把画面转成结构化数据，再喂给 Jev 做判断**，而不是让它直接看截图。

## 九、结论

Jev 的价值不在于"更聪明"，而在于**把软件里大量的小判断从"解析散文"变成"读一个带概率的类型化结果"**。

**它成立的地方**：高频、单次后果轻、答案空间封闭、需要语义判断但又写不出干净的 if。速度快、价格低（输入 $0.042/百万 token、输出免费）、结果可校准，很适合作为**决策模型接入自家 AI 应用**——智能客服、内容审核、批量打标签、Agent 路由与门控，能把**成本和延迟**同时打下来。

**它不成立的地方**：任何要生成文字的场景、任何多步推理、任何算术与日期比较。它取代不了 LLM，正确姿势是**分工**——LLM 规划与撰写，Jev 判断与门控。

**三条落地建议**：

1. **别把它当 ChatGPT 用**。上手前先接受"它不会写文字"这个前提，否则预期会完全错位。
2. **优先在批量分类/打标签场景试点**。视频里表现最稳的就是 1000 封邮件分类和 697 篇打标签，投入产出比最容易验证。
3. **记住"保证形状，不保证决策"**。类型安全只解决了答案的**结构**问题，不解决**对错**问题——所以关键动作外面必须留一层应用层防护和人工兜底，并且用你自己的代表性数据去定阈值、测准不准。

一句可以直接背下来的话：**Jev 不是更会聊天的 AI，是让代码不用再猜 AI 意思的那种 AI。**
